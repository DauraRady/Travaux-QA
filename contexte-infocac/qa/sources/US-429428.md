## Description

### User Story

En tant qu'Admin ou SuperAdmin ayant créé une demande, je veux retrouver dans le formulaire les informations renseignées ou générées lors de la création de la demande afin de conserver la continuité des données et d'éviter toute ressaisie.

### Périmètre des règles de gestion

CHANGEMENT Cette US couvre la persistance des informations suivantes entre la Nouvelle demande et le formulaire créé :
- Type de mandat
- Catégorie du mandat
- N° engagement

Les données sont restituées dans les emplacements prévus par la maquette :
- Type de mandat : section Description du mandat
- Catégorie du mandat : section Description du mandat
- N° engagement : section Description du mandat

Sont exclus de cette US :
- les règles de saisie et de sélection du Type de mandat ;
- les règles de format du N° engagement ;
- la logique d'affectation ou de réaffectation d'une demande ;
- la modification des données après validation ;
- les autres champs de la section Description du mandat.

### Flow utilisateur

L'utilisateur crée une Nouvelle demande.
Au cours de cette création, les informations nécessaires à l'initialisation du formulaire sont renseignées ou déterminées :
- Type de mandat
- N° engagement
- Affecté à
- Entité ID

Lorsque la Nouvelle demande est créée, ces informations sont persistées et rattachées à la demande.
À l'ouverture du formulaire :
- l'utilisateur retrouve automatiquement le Type de mandat ;
- l'utilisateur retrouve automatiquement le N° engagement ;
- l'Affecté à est affiché dans la section Description du mandat ;
- l'Entité ID est affiché dans l'en-tête du formulaire.

Aucune ressaisie n'est nécessaire.

### Étape 1 : Données provenant de la Nouvelle demande

RG-PERSIST-DM-01 : Lors de la création de la Nouvelle demande, le système conserve les informations suivantes : Type de mandat ; N° engagement ; Affecté à ; Entité ID.
Chaque information est rattachée à l'identifiant de la demande créée.
Le passage de la fenêtre Nouvelle demande au formulaire ne doit pas :
- supprimer une valeur ;
- réinitialiser une valeur ;
- remplacer une valeur par une valeur par défaut différente ;
- associer une valeur appartenant à une autre demande.

### Étape 2 : Persistance du Type de mandat

RG-PERSIST-DM-02 : La valeur de Type de mandat enregistrée lors de la création est automatiquement restituée dans le champ Type de mandat de la section Description du mandat.
Pour la France, les valeurs prévues par l'US Description du mandat sont : Certification des comptes ; Durabilité ; Certification des comptes & Durabilité.
La valeur affichée doit correspondre à celle enregistrée lors de la création de la demande.
L'utilisateur n'a pas à sélectionner de nouveau le Type de mandat à l'ouverture du formulaire.

### Étape 3 : Persistance du N° engagement

RG-PERSIST-DM-03 : Le N° engagement renseigné lors de la création est persisté avec la demande.
À l'ouverture du formulaire :
- le champ N° engagement de Description du mandat contient la valeur enregistrée lors de la création ;
- aucune nouvelle saisie n'est nécessaire ;
- la création du formulaire ne remet pas le champ à vide.
La maquette fournie matérialise bien N° engagement comme un champ de la section Description du mandat.

### Étape 6 (fin)

Lors de la première ouverture du formulaire, le système garantit la correspondance entre les données de la Nouvelle demande et les données restituées.
Les correspondances attendues sont :
- Type de mandat Nouvelle demande → Type de mandat Description du mandat
- N° engagement Nouvelle demande → N° engagement Description du mandat
- Affecté à Nouvelle demande → Affecté à affiché dans Description du mandat
- Entité ID Nouvelle demande → Entité ID affiché dans l'en-tête du formulaire

L'initialisation du formulaire ne doit pas modifier les valeurs persistées.

### Étape 7 : Réouverture d'une demande

RG-PERSIST-DM-07 : Lorsque l'utilisateur quitte puis rouvre une demande : Type de mandat conserve sa valeur ; N° engagement conserve sa valeur ; Affecté à conserve sa valeur ; Entité ID conserve sa valeur.
La navigation entre différents écrans ou la fermeture du formulaire ne doit pas provoquer la perte de ces informations.

### Étape 8 : Isolation des données entre les demandes

RG-PERSIST-DM-08 : Les informations sont persistées au niveau de chaque demande.
Si plusieurs demandes existent, chaque demande conserve indépendamment : son Type de mandat ; son N° engagement ; son Affecté à ; son Entité ID.
Les données d'une demande ne doivent jamais être affichées dans le formulaire d'une autre demande.

### Étape 9 : Gestion d'un échec de persistance

RG-PERSIST-DM-09 : La persistance des quatre informations doit être cohérente avec la création de la demande.
Si une erreur technique empêche la persistance de l'une des données :
- l'erreur ne doit pas être silencieuse ;
- le système ne doit pas présenter une valeur manquante comme correctement enregistrée ;
- l'utilisateur doit être informé de l'erreur.

Le comportement à appliquer à la création en cas d'échec partiel reste à arbitrer :
- refus complet de création ;
- ou création de la demande avec signalement d'une anomalie.
